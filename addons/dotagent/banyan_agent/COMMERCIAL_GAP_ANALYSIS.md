# Banyan Agent 商用能力差距分析（2026-08-01）

> 评估背景：R9–R22 共 14 轮真实任务驱动（纯分析/微改动/跨节点功能/新域创建四类），
> 全部数据来自 `banyan_agent/sessions/*/run_*.json` 与 `tests/_trace_analyze.py` 的诊断。
> 本文档是后续优化的基准线，随里程碑更新。

## 一句话结论

**在它被调过的窄域（本项目小型 Godot 功能开发）约达商用线 70%；作为通用商用开发 agent 约 40–50%。**
树状专家架构的天花板高于市面扁平 agent，但工程闭环差距明显。

## 差距清单（按严重度排序）

### ❶ 无运行时闭环（最致命）→ 本轮开发
- **问题**：agent 不会"跑起来验证"。17 个场景 script 集体挂空数周未被发现——
  它只能做静态检查（语法/结构），无法发现空引用、信号断连、节点路径错误。
- **目标**：`run_game_check` 工具（无头实跑 → 抓运行时错误 → 结构化返回），
  实现类任务收尾前自动实跑验证。

### ❷ 单项目单模型调参（暂缓）
- **问题**：全部优化围绕本仓库 + MiniMax-M2.7 的怪癖。换代码库/换模型成功率未知。
- **暂缓原因**：owner 指示先做 ❶❸❹。

### ❸ 无任务成功率度量 → 本轮开发
- **问题**：只有机制级回归测试，没有"N 个任务成几个"的数字。商用产品靠基准说话。
- **目标**：`tests/benchmark/` 任务集（20+ 任务带断言）+ 批量驱动 + 评分报告，
  成功率成为可追踪指标。

### ❹ 长任务会死 → 本轮开发
- **问题**：R17 新域任务 290s 被杀，子节点知识/用量全部丢失（进程杀前未存树）。
- **目标**：看门狗触发时优雅收束（abort 信号 → 节点收敛）+ 运行中定期存树，
  被杀也不丢沉淀。

### ❺ 无规划层（观察中）
- 逐轮反应式推进，大任务会漂。等 ❶❸❹ 落地后用基准数据评估是否需要。

## 基准驱动的意外修复（首轮跑出）

基准第一跑就抓到三个致命健壮性 bug（此前隐藏数周）：

1. **HTTP 状态机在 TLS 传输错误后永久挂起**：`_poll_waiting` 对 CONNECTION_ERROR/TLS_HANDSHAKE_ERROR 等状态"重试下一帧"死循环（mbedtls -0x6c00 后挂 270s+ 直到外部 kill）。修复后 1 帧内快速失败进退避重试。回归 6/6。
2. **空闲看门狗被流式心跳喂假活动**：LLM 等待循环每 0.5s 重发同状态心跳，挂死期间照发，看门狗永不触发。驱动器改为按状态去重记活动。
3. **API key 未 strip**：shell 提取环境变量带入前导换行，拼出 `Bearer \n\nsk-...` 非法请求头被服务器 400 断连（曾误诊为网络故障）。`get_api_key()` 已加固。

另发现一个行为浪费并当场修复：**同参数连败**（X3 首轮 replace_in_file 同参数连挂 3 次烧 148k）→ 新增连败守卫（同工具+同参数连挂 2 次注入换路提醒），X3 复测 **148.6k/204s → 10.6k/31s（-93%）**。
