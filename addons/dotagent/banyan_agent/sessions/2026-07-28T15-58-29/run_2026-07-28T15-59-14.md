## 2. 副武器 alt_ammo 散射逻辑：可小改进点

### 2.1 `alt_ammo` 当前未实际生效
**问题**：虽然导出了 `alt_ammo`，但 `fire_spread()` 没有检查弹药量。  
**建议**：
```gdscript
if Input.is_action_pressed("alt_shoot") and alt_fire_timer <= 0:
    if alt_ammo == 0 or alt_ammo > 0 and alt_ammo > 0:  # 当前无扣减
        fire_spread()
        if alt_ammo > 0:
            alt_ammo -= 1
        alt_fire_timer = 0.4
```
或者更简洁：
```gdscript
if alt_ammo != 0:
    alt_ammo = max(0, alt_ammo - 1)
```
并在 HUD 上显示剩余弹药。

### 2.2 散射方向硬编码，可参数化
当前 5 发散弹的角度是 magic number：
```gdscript
var far_left  = Vector2(-0.7, -1).normalized()
var up_left   = Vector2(-0.4, -1).normalized()
var up        = Vector2.UP
var up_right  = Vector2(0.4, -1).normalized()
var far_right = Vector2(0.7, -1).normalized()
```
**建议**：用 `spread_count` 和 `spread_angle` 参数化，便于后续调整平衡。例如：
```gdscript
const ALT_SPREAD_COUNT := 5
const ALT_SPREAD_ANGLE := 0.7  # 弧度总张角
func fire_spread():
    _am().play_sfx("shoot")
    var center = position + Vector2(0, -30)
    for i in ALT_SPREAD_COUNT:
        var t = (i / float(ALT_SPREAD_COUNT - 1)) * 2.0 - 1.0  # -1 .. 1
        var angle = t * ALT_SPREAD_ANGLE
        var dir = Vector2.UP.rotated(angle)
        var offset_x = (i - ALT_SPREAD_COUNT / 2) * 2.0
        shoot_spread.emit("res://scenes/bullet.tscn", center + Vector2(offset_x, 0), dir)
```
这样 5 发散弹、7 发散弹或扇形角度都可以只改常量。

### 2.3 副武器发射位置只按 `position` 计算，没有考虑 Dash 或位移
**问题**：`fire_spread()` 的 `center = position + Vector2(0, -30)` 在 `_process` 末尾调用，此时 `position` 已经被 Dash 分支提前 `return` 处理过，主分支时正常。但逻辑上，如果以后 Dash 中允许射击，会错位。  
**建议**：把枪口偏移做成常量 `MUZZLE_OFFSET = Vector2(0, -30)`，统一使用，并在 `fire()` 中也复用。

### 2.4 副武器发射间隔与导出值不一致
- 导出 `alt_fire_rate = 0.35`，但 `_process` 里写死 `alt_fire_timer = 0.4`。  
**建议**：使用 `alt_fire_rate` 而不是 magic number。

## 3. 子弹生命周期管理：可小改进点

### 3.1 `bullet.gd` 每帧调用 `get_viewport_rect()`
```gdscript
func _in_bounds() -> bool:
```

**建议**：缓存 viewport size，或只在窗口大小变化时更新。例如：
```gdscript

    _bounds = get_viewport_rect().grow(50)
    get_viewport().size_changed.connect(_update_bounds)
func _update_bounds():
    _bounds = get_viewport_rect().grow(50)
func _in_bounds() -> bool:
    return _bounds.has_point(position)
```
或者让 `game.gd` 在创建时把边界传进来。

## 分析结论：16 路 SFX 复用池在高频连发下存在正确性与体验隐患，性能风险相对可控但存在改进空间。

下面按性能、正确性、可扩展性三个维度逐项说明，并给出具体建议。

---

### 1. 核心逻辑回顾

`res://scripts/audio_manager.gd` 的 SFX 池关键代码：

```gdscript
const POOL_SIZE = 16

func _ready():
    _sfx_players.resize(POOL_SIZE)
    for i in POOL_SIZE:
        var p = AudioStreamPlayer.new()
        p.bus = "Master"
        add_child(p)
        _sfx_players[i] = p

func play_sfx(type):
    var stream = _get_sfx_stream(type)
    if stream == null:
        return

    for p in _sfx_players:          # 优先找空闲
        if not p.playing:
            _configure_player(p, stream)
            return

    # 全忙：停止最旧的一个并复用
    var oldest = _sfx_players[0]
    oldest.stop()
    _configure_player(oldest, stream)

func _configure_player(p, stream):
    p.stream = stream
    p.volume_db = randf_range(-3, 0)
    p.pitch_scale = randf_range(0.92, 1.08)
    p.play()
```

SFX 通过 `_sfx_cache` 缓存生成的 `AudioStreamWAV`，避免重复生成 WAV 数据。

---

### 2. 性能隐患

#### 2.1 16 路池在极端高频下可能不足

- 玩家武器 `fire_rate = 0.18`，约 5.5 发/秒，单类型 `shoot` 约 0.09 秒。
- 同屏若有多个 Fighter/Bomber/Carrier 敌人同时射击，加上 `hit`、`explode` 等命中/爆炸，某一帧内并发请求可能超过 16 个。
- 当前实现会直接截断数组下标 `0` 的播放器，导致**不是真正“最老”的声音被截断**，而是固定位置的声音被反复截断。

**建议**：  
引入“真实最老”选择策略（记录每个播放器的开始时间或剩余时间），或者改用 Round-Robin，避免固定下标 `0` 被反复抢占。

#### 2.2 每次播放都重新设置 `stream`

```gdscript
p.stream = stream
p.play()
```

即使 `stream` 与当前相同，也会触发一次重新赋值。对 `AudioStreamWAV` 这种内存流来说开销很小，但如果同一播放器被频繁复用，连续 `stop()` + `play()` 在极端帧率下可能产生轻微爆音或延迟。

**建议**：  
若新请求与当前播放器在播放的是同一 `stream`，可直接 `play()` 不重置 `stream`（但需重新设置 pitch/volume）。不过在 Godot 4 中，AudioStreamPlayer 单实例不能同时播放同一 stream 多次，所以仍需多实例。

#### 2.3 高频随机调用

`_configure_player` 中：

```gdscript
p.volume_db = randf_range(-3, 0)
p.pitch_scale = randf_range(0.92, 1.08)
```

每次播放调用 2 次 `randf()`，性能开销可忽略，但连发时随机变化是有意设计，无需改动。

#### 2.4 缓存机制有效，但无并发类型控制

`_sfx_cache` 确保同一类型 SFX 只生成一次 WAV，消除了重复生成内存流的 CPU 开销。  
但没有限制**同一类型同时播放的最大数量**。例如多个敌人同时爆炸，0.5 秒的 `explode` 会瞬间占满多个声道，导致后续 `hit` 或 `shoot` 被截断。

**建议**：  
为 `explode`、`hit` 等高频短音增加 polyphony 限制，例如同类型最多同时播放 4 路。

---

### 3. 正确性/体验隐患

#### 3.1 “最旧”选择策略不正确

```gdscript
var oldest = _sfx_players[0]
oldest.stop()
_configure_player(oldest, stream)
```

这里不是“最旧”，而是“固定位置 0”。  
由于 `for p in _sfx_players` 从头遍历找空闲，下标靠前的播放器会被更频繁地分配；当下标 0 在忙时，总是优先找下标 1、2 等。结果是：

- 某些声音可能刚播放就被截断；
- 下标 0 被反复截断，下标 15 几乎不会被截断；
- 无法保证真正最早开始的声音保留。

**建议**：  
改为按 `playback_position` 或记录开始时间 `start_time` 排序，找出真正最短的播放器进行替换。

#### 3.2 没有优先级分类，重要音效可能被截断

SFX 类型包括短音：

- `shoot`：0.09 秒
- `click`：0.04 秒
- `hit`：0.2 秒
- `damage`：0.25 秒

中长音：

- `explode`：0.5 秒
- `powerup`：0.45 秒
- `wave`：0.6 秒
- `warning`：0.5 秒
- `gameover`：1.2 秒

当前实现中，一个 `shoot` 请求可以把正在播放的 `gameover` 或 `warning` 直接截断。

**建议**：  
引入优先级：重要/长音（`gameover`、`warning`）不应被短音替换；或者为 `gameover` 单独分配不可被抢占的播放器。

#### 3.3 没有冷却与去重机制

高频连发时，可能出现同一帧内多次触发同类型音效（例如多颗子弹同时命中同一目标）。  
当前代码会占用多个声道播放几乎相同的声音，造成音量叠加和失真。

**建议**：  
- 对 `shoot`/`hit` 等高频音效添加同类型触发冷却，例如 50ms 内同一类型只触发一次。
- 对 `click` 等 UI 音，由于其本身 0.04 秒，影响不大，但也可限制。

#### 3.4 音乐与 SFX 没有分离

虽然 `_music_player` 是独立实例，但：

```gdscript
if _music_player.playing:
    _music_player.stop()
_music_player.stream = stream
_music_player.play()
```

如果当前播放的就是同一首 track，调用 `play_music` 仍会重新播放，而不是继续播放。这不是 SFX 池的问题，但与音频管理相关。

**建议**：  
若请求播放的音乐已在播放，可跳过；如需循环切换，支持无缝/淡入淡出。

#### 3.5 所有声音共用 Master Bus，无动态压缩

大量 SFX 并发时，Master 总线会出现削峰/失真，尤其在多个爆炸同时播放时。

**建议**：  
- 为 SFX 和 Music 分别使用 `SFX`、`Music` 总线。
- 在 SFX 总线上添加 Compressor/Limiter，避免峰值过载。
- 爆炸时加入侧链闪避（Ducking），让音乐自动降低。

---

### 4. 高频连发场景具体估算

以典型战斗场景为例：

| 来源 | 频率 | 时长 |
|---|---|---|
| 玩家射击 | ~5.5/秒 | 0.09s |
| 5 个 Fighter 敌人射击 | ~3/秒 × 5 = 15/秒 | 0.09s |
| 命中火花 | 10-20/秒 | 0.04-0.2s |
| 爆炸 | 2-5/秒 | 0.5s |

在最密集的 0.5 秒窗口内，并发请求可能达到 20-30 个，超过 16 路池。  
虽然大多数音效很短，会快速释放，但连续触发时仍会导致：

1. 频繁抢占；
2. 枪声音被截断，产生断断续续感；
3. 重要长音（`gameover`、`warning`）被意外覆盖。

---

### 5. 具体改进建议（不修改代码）

1. **修正“最旧”选择逻辑**
   - 记录每个播放器的开始时间或剩余时间，替换时选择真正最短/最旧的。
   - 或采用 Round-Robin，避免固定下标 0 被反复抢占。

2. **引入优先级与不可抢占声道**
   - 为 `gameover`、`warning` 设置高优先级，不应被 `shoot`/`hit` 截断。
   - 可为重要音效保留 1-2 个专用播放器。

3. **限制同类型并发数量**
   - 例如 `explode` 最多同时 4 路，`shoot` 最多 6 路，`hit` 最多 4 路。
   - 超出时忽略或复用同类型正在播放的播放器。

4. **添加同类型触发冷却**
   - 对 `shoot`、`hit` 等短音，限制 30-50ms 内同类型只能触发一次。
   - 减少声道争夺和音量叠加。

5. **扩大池容量**
   - 若战斗场景确实高频，可将 `POOL_SIZE` 从 16 提升至 24 或 32。
   - 但需配合总线限制器，避免混音失真。

6. **考虑使用 AudioStreamPolyphonic**
   - Godot 4 支持 `AudioStreamPolyphonic`，单个播放器可同时播放多个 voice。
   - 对 `shoot` 这类高频短音，可用一个 Polyphonic 播放器管理多 voice，减少池需求。

7. **分离总线并添加动态压缩**
   - 创建 `SFX` 和 `Music` 总线。
   - SFX 总线添加 Compressor 或 Limiter。
   - 爆炸时加入 Ducking，让音乐自动降低。

8. **避免截断爆音**
   - 替换前可设置极短 fade-out（若 Godot 版本支持）。
   - 或至少对长音设置 `play()` 前不 `stop()`，而是标记为待释放，等自然结束。

9. **增加调试计数**
   - 记录当前活跃 SFX 数量、每秒截断次数、缓存命中次数。
   - 便于验证改进效果。

---

### 6. 总结

- **性能**：当前缓存机制消除了重复生成 WAV 的开销，16 路池在普通场景够用；但极端高频连发时存在并发不足的风险。
- **正确性**：最大隐患是“最旧”选择实际为固定下标 0，加上无优先级、无类型并发限制，会导致重要音效被截断、混音不均匀。
- **建议优先级**：修正最旧选择 > 引入优先级/保留声道 > 同类型并发限制 > 触发冷却 > 扩大池/使用 Polyphonic > 总线压缩。


## Summary

两个子节点的报告均已拿到。下面是并行分析的对比汇总：

---

## 1. PlayerCombat 报告核心发现

### 主要问题

| 问题 | 说明 | 建议 |
|---|---|---|
| `alt_ammo` 未实际生效 | 导出了变量但 `fire_spread()` 没有检查或扣减 | 检查 `alt_ammo` 并在发射时扣减，0 表示无限 |
| 散射方向硬编码 | 5 发散弹的 5 个方向向量都是 magic number | 用 `spread_count` + `spread_angle` 参数化 |
| 发射间隔不一致 | 导出 `alt_fire_rate = 0.35`，但代码写死 `0.4` | 统一使用 `alt_fire_rate` |
| 子弹越界检测每帧取 viewport | `get_viewport_rect()` 每帧调用 | 缓存 viewport rect 或边界矩形 |
| 两套子弹系统并存 | 有 `bullet_pooled.gd` + `Pool.gd`，但 `game.gd` 仍直接 `instantiate()/queue_free()` | 逐步切换到池化，减少 GC |
| 枪口偏移 magic number | `Vector2(0, -30)` 重复出现 | 提取常量 `MUZZLE_OFFSET` |
| `bullet_pooled.gd` 冗余短路 | `has_node(...) or true` 永远为 true | 清理该表达式 |

### 架构建议
- 统一 `shoot` 信号，减少信号数量
- 把武器等级配置拆成资源或字典
- 合并 `game.gd` 中两个几乎相同的 shoot handler

## 2. AudioGlobals 报告核心发现

### 主要问题

| 问题 | 说明 | 建议 |
|---|---|---|
| "最旧"选择逻辑不正确 | 全忙时总是截断 `_sfx_players[0]`，不是真正最旧 | 按 `playback_position` 或开始时间排序，或 Round-Robin |
| 16 路池在高频下可能不足 | 估算并发可达 20-30 个 | 扩容到 24/32，或引入类型限制 |
| 无优先级 | 短音 `shoot` 可能截断长音 `gameover`/`warning` | 引入优先级，为重要音效保留专用声道 |
| 无同类型并发限制 | 多个敌人同时爆炸会占满声道 | 限制同类型最大同时播放数（如 `explode` 最多 4） |
| 无触发冷却 | 同一帧内重复触发会叠加失真 | 对高频短音加 30-50ms 冷却 |
| 总线未分离 | 所有声音走 Master | 创建 SFX/Music 总线，加 Compressor/Limiter |
| 未使用 AudioStreamPolyphonic | Godot 4 支持单播放器多 voice | 对 `shoot` 等高频短音使用 Polyphonic |

---

## 3. 对比汇总

### 共同关注点

| 维度 | PlayerCombat | AudioGlobals |
|---|---|---|
| **高频压力** | 子弹大量实例化/销毁 | 16 路 SFX 池被高频请求填满 |
| **硬编码/magic number** | 散射方向、发射间隔、枪口偏移 | 池大小、优先级、选择策略 |
| **性能隐患** | 每帧 `get_viewport_rect()`、未池化 | 固定截断、无并发限制 |
| **正确性/体验隐患** | `alt_ammo` 无效 | 重要音效被截断、混音失真 |

### 建议优先级

1. **修复 Audio 最旧选择逻辑** — 这是正确性 bug，应优先修
2. **让 `alt_ammo` 实际生效** — 玩法完整性
3. **统一 Player 副武器发射间隔与参数化散射**
4. **Audio 引入优先级 + 保留声道 + 同类型并发限制**
5. **优化子弹越界检测缓存**
6. **统一使用子弹池化** — 架构级改进
7. **Audio 总线分离与动态压缩** — 体验提升

---

## 4. 结论

- **PlayerCombat**：主要是可维护性和玩法完整性问题，以及未池化导致的潜在 GC 压力。
- **AudioGlobals**：主要是正确性 bug（固定截断）和并发管理不足，在高频连发场景下会有明显体验问题。

两个模块都建议优先处理"正确性"类的小 bug（Audio 的截断逻辑、Player 的 alt_ammo 失效），再逐步做参数化和性能优化。
